# 评分细则

每个项目按四个维度打分，总分 100。评分依据必须来自实际抓取的数据，禁止凭印象编造。

## 1. 受欢迎度 Popularity（25 分）

| 指标 | 依据 |
|---|---|
| 周期增长 | Trending 周期内新增 Star 数（today / weekly / monthly） |
| 总认可度 | 仓库总 Star 数、Fork 数 |

打分参考：

- 周期新增 Star ≥ 1000 → 15-25 分
- 500-999 → 10-14 分
- 100-499 → 5-9 分
- < 100 → 0-4 分
- 总 Star ≥ 10k 可加 0-5 分（长期认可度）；总 Star < 100 且无增量，本维度不高于 10 分

## 2. 维护活跃度 Maintenance（25 分）

| 指标 | 依据 |
|---|---|
| 最近提交 | 仓库页显示的最近 commit 时间 |
| 版本发布 | 最近 release / tag 时间 |
| 问题处理 | Open Issues 数量是否与项目规模匹配（规模越大容忍度越高） |

打分参考：

- 近 1 个月有活跃提交且近期有 release → 18-25 分
- 近 3 个月有提交 → 10-17 分
- 近半年有提交 → 5-9 分
- 超半年无提交 → 0-4 分，并在点评中标记「维护风险」

## 3. 实用性与可应用性 Practicality（30 分）

| 指标 | 依据 |
|---|---|
| 用途明确 | README 是否清楚说明解决什么问题、目标用户是谁 |
| 可落地 | 是否有安装/使用文档、CLI / API / 示例 / 教程 |
| 采用度 | README 中 used-by、生产引用、下载量等证据 |
| 场景匹配 | 是否适合用户的使用意图（学习、选题、直接使用、集成） |

打分参考：

- 用途清晰 + 文档示例齐全 + 可立即使用 → 22-30 分
- 用途清晰但上手成本高 / 文档不全 → 12-21 分
- 概念验证 / 玩具项目 / 用途模糊 → 0-11 分

## 4. 技术栈与质量 Quality（20 分）

| 指标 | 依据 |
|---|---|
| 技术主流性 | 使用主流语言/框架，社区生态成熟 |
| 工程规范 | 有 LICENSE、CI、清晰的目录结构、测试 |
| 工程形态 | 完整工程优于单文件脚本/实验性实现 |

打分参考：

- 主流技术栈 + 工程规范完整 → 15-20 分
- 技术合理但工程不完整 → 8-14 分
- 小众/实验性技术、结构混乱 → 0-7 分

## 总分与评级

| 总分 | 评级 | 结论 |
|---|---|---|
| 90-100 | S 强烈推荐 | 值得立即使用 / 深入学习 |
| 75-89 | A 推荐 | 有价值，值得关注 |
| 60-74 | B 值得关注 | 有一定价值，留意后续发展 |
| < 60 | C 一般 | 暂不值得投入时间 |

## 点评要求

每个项目附加 1-2 句点评：

- **价值点**：解决了什么问题、为什么值得关注、适合谁用
- **风险点**（如有）：维护停滞、文档缺失、过度炒作、License 限制等

点评用中文，具体到该项目，不使用套话。
